# 领域建模

在设计的同时，主动去构建并磨利项目的领域模型。这是一门*主动*的功夫：质疑用词、构造边界场景，并在术语和决策刚刚定形的当下就把它们写下来。（只是翻 `GLOSSARY.md` 查词，不算这个 skill：那是一行就能做到的日常习惯，任何 skill 都能顺手做。这个 skill 用在你要**改动**模型的时候，而不只是取用它。）

## 文件结构

多数仓库只有一个上下文：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `GLOSSARY-MAP.md`，说明仓库有多个上下文。这张 map 会指出每个上下文在哪里：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 该上下文专属的决策
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

文件按需创建：真有东西要写了才建。没有 `GLOSSARY.md` 时，等第一个术语定下来再建；没有 `docs/adr/` 时，等需要第一个 ADR 时再建。

## 会话过程中的做法

### 拿术语表来挑冲突

用户用某个术语，而它与 `GLOSSARY.md` 里既有的语言相冲突时，立刻指出来。"你的术语表把 'cancellation' 定义成 X，但你这会儿说的似乎是 Y。到底是哪个？"

### 把模糊的说法磨准

用户用了含糊或一词多义的词时，给出一个精确的、规范的说法。"你说的 'account'：指的是 Customer 还是 User？这是两回事。"

### 拿具体场景来压

讨论领域关系时，用具体场景对它们做压力测试。构造能探到边界的场景，逼着用户把概念之间的边界说清楚。

### 与代码交叉核对

用户说某件事是怎么运作的，就去核对代码是不是同一个说法。发现矛盾就摆出来："你的代码会把整张 Order 取消掉，可你刚说部分取消是可能的。哪个才对？"

### 当场更新 GLOSSARY.md

一个术语定下来，就在那儿当场更新 `GLOSSARY.md`。别攒着一起写：发生一个就记一个。格式用 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)。

`GLOSSARY.md` 里应当完全不出现实现细节。别把 `GLOSSARY.md` 当规格文档、草稿纸，或实现决策的存放处。它就是一份术语表，仅此而已。

### 尽量少提 ADR

只有以下三条同时成立，才提议建 ADR：

1. **难以逆转**：日后反悔的代价是实打实的
2. **脱离上下文会让人意外**：未来的读者会想"他们到底为什么这么做？"
3. **是真实取舍的结果**：确实存在其他可选方案，而你出于具体理由选了这一个

三条里缺任何一条，就跳过 ADR。格式用 [ADR-FORMAT.md](./ADR-FORMAT.md)。
