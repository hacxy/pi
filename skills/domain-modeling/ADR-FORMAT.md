# ADR 格式

ADR 放在 `docs/adr/` 下，按顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

`docs/adr/` 目录按需创建：只有需要第一个 ADR 时才建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：上下文是什么，我们决定了什么，以及为什么。}
```

就这样。一份 ADR 可以只有一段话。它的价值在于记下**做过**这个决策以及**为什么**，而不在于把各个小节填满。

## 可选小节

只有确实有价值时才加。多数 ADR 用不到。

- **Status** 前置元数据（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：在决策会被重新翻出来看时有用
- **Considered Options（考虑过的方案）**：只有被否掉的方案值得记住时才写
- **Consequences（后果）**：只有存在不显然的下游影响需要点明时才写

## 编号

扫一遍 `docs/adr/`，取现有最大编号加一。

## 何时提议 ADR

以下三条必须同时成立：

1. **难以逆转**：日后反悔的代价是实打实的
2. **脱离上下文会让人意外**：未来的读者看到代码会想"他们究竟为什么这么做？"
3. **是真实取舍的结果**：确实存在其他可选方案，而你出于具体理由选了这一个

如果决策很容易逆转，就跳过：反正你到时候直接改回来就行。如果它不让人意外，没人会去问为什么。如果没有真正的可选方案，那除了"我们做了显而易见的那件事"之外，也没什么可记的。

### 什么情况值得记

- **架构形态。** "我们用 monorepo。""写模型是事件溯源的，读模型投影到 Postgres。"
- **上下文之间的集成方式。** "Ordering 与 Billing 通过领域事件通信，而不是同步 HTTP。"
- **会形成锁定（lock-in）的技术选型。** 数据库、消息总线、认证服务商、部署目标。不是每个库都记：只记那些换掉要花一个季度的。
- **边界与范围决策。** "客户数据由 Customer 上下文拥有；其他上下文只按 ID 引用。"明确的"不做"和"做"一样有价值。
- **刻意偏离显而易见的路。** "因为 X，我们用手写 SQL 而不是 ORM。"凡是合理读者会默认相反做法的地方都算。这类记录能拦住下一位工程师去"修好"某个本来就是故意的设计。
- **代码里看不见的约束。** "由于合规要求，我们不能用 AWS。""由于合作方的 API 合约，响应时间必须低于 200ms。"
- **被否掉的方案，且否掉的理由不显然。** 如果你考虑过 GraphQL、因为某些微妙的理由选了 REST，就记下来；否则半年后又有人会提议上 GraphQL。
